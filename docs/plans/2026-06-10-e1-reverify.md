# Episode E1 — Scheduled re-verification engine

**Status:** Critic-reviewed and locked (R1 closed 3 must-fix + 1 med + 1 low; R2 pinned 5 execution advisories). Implemented on branch `feat/e1-reverify`.

**Goal:** `reliability_score` is computed ONCE at publish time (`push.ts` → eval runner; importers → `applyKindEval`). A tool that rots after publish — upstream API change, stub regression, contract drift — is only caught when a USER'S AGENT eats the failure live (`call.ts` ajv violation → `circuit_broken`). STRATEGY.md names the missing primitive: "CI layer — every tool change triggers an eval suite... continuously re-ranks tools." E1 builds the re-verification core.

**Baseline:** typecheck clean, 161/161 tests. Scope: one PR. No npm publish; fly deploy is a separate human-gated op.

**Non-negotiables enforced:** real DB tests (no mocks, rule 5); writes go through `Storage` interface (rule 1); first-party stubs only (rule 12); SQLite writes queue-serialized (rule 13).

---

## 1. `src/services/reverify.ts` (new service) + shared eval invocation (R1 must-fix 1)

**Grader-policy parity (CRIT fix):** push.ts's eval invocation — including the `malformed_bot_lenient_override` applied when `endpoint_stub_name === 'malformed-bot-v1'` ("Fix 11") — is factored into a shared helper (`src/services/runToolEvals.ts`) that BOTH `push.ts` and `reverifyTools` call. Reverify thereby re-runs the EXACT publish-time suite: the `eval_runs` time series never mixes grader policies, and a sweep cannot strict-grade and gate-drop the rule-8 demo's malformed-bot tool. Test asserts malformed-bot's score is UNCHANGED by reverify.

`reverifyTools(storage: Storage, opts?: { toolName?: string; toolVersion?: string })` → per-tool partition (THE trap found at discover — `runEvals` returns `pass_rate: 0` for any tool without a `STUB_DOMAIN` entry; a naive sweep would zero every scraped catalog tool and empty the registry through the 0.80 gate):

- `tool_kind === 'tool'` AND `STUB_DOMAIN[endpoint_stub_name]` exists AND the suite has cases (`total_count > 0` — R1 low: a 0-case domain must not zero a score either) → shared-helper eval run, `insertEvalRun` with `triggered_by: 'reverify'`, then `updateToolAfterEval(tool.id, metadata, tool.status)` — **status passed through verbatim** (the storage impl writes the caller-supplied status; push passes `'active'`, reverify passes the CURRENT status, which is what preserves `circuit_broken`). Score = latest pass_rate (publish semantic; decay/blend is E2's).
- `tool_kind === 'tool'` with NO eval suite (unknown stub) → summary `skipped: 'no-eval-suite'`. NEVER write a score. NEVER insert an empty eval run.
- Catalog kinds (skill/subagent/prompt) → `skipped: 'catalog-kind'`.
- `status === 'pending'` → `skipped: 'pending-status'` (a lingering pending row is an incomplete publish; the sweep must not promote or score it).
- `status === 'circuit_broken'` → evals RUN and are recorded (feeds E2's recovery), score updates, status preserved via pass-through — D34: only `call.ts` flips to `circuit_broken`; recovery is E2. Code comment states this.

Returns `{ executed, passed, failed, skipped: [{name, version, reason}], gate_dropped: [names] }` where `gate_dropped` = tools whose new score fell below 0.80 this run.

## 3. `triggered_by` (verified reality — R1 must-fix 3)

`eval_runs.triggered_by` is unconstrained TEXT (`001_init.sql`); the TS union (`EvalRunRow` in `src/types.ts`) was `'push' | 'manual' | 'scheduled'`. Change: widen the union with `'reverify'` and use **'reverify' for BOTH trigger paths** (CLI/route and interval) so the time series is queryable on one value. NO migration.

## 4. Surfaces

- **Route** `POST /v1/reverify` (body `{ tool_name?, tool_version? }`) in `src/server/routes/reverify.ts`. Auth (R1 med): the UNFILTERED sweep is **admin-only** (it re-scores every author's tools and holds a long request open); a single-tool filtered reverify accepts `['tool_author','admin']`, mirroring push. A tool_author may re-score other authors' tools via the filtered path — suites are deterministic, so this is benign. Returns the summary.
- **CLI** verb `2chain reverify [--tool name@version]` in `bin/2chain.mjs`, printing the summary (executed/passed/failed/gate-dropped/skipped).
- **Opt-in interval**: `REVERIFY_INTERVAL_MIN` env (default unset = OFF) → `setInterval` in `buildServer()` calling `reverifyTools`; logs the summary via pino; in-flight boolean guard so a slow sweep never overlaps the next tick. Off by default so fly.io / laptop deployments opt in deliberately (no surprise CPU).

## 5. Tests (real SQLite, NO mocks — non-negotiable rule 5)

**Rot construction, named (R1 must-fix 2).** Deterministic first-party stubs cannot rot on their own — publish score equals reverify score forever without an explicit state change. The test constructs rot with NO mocks: ONE first-party deterministically-FAILING eval stub (`rotten-pdf-v1`, registered inline in `src/services/stubs.ts` next to the sibling pdf stubs — `src/tools/` is for real network fetchers — and in `STUB_DOMAIN` under `'pdf-extraction'`, returning `{rows: []}` which violates every pdf-domain `numeric_tolerance` grader; rule-12 compliant, used by no seeded/demo tool so it is inert outside tests). The test publishes a real tool pointing at the healthy pdf stub (passes ≥ gate), then simulates upstream rot via a direct test-side SQL UPDATE re-pointing its `endpoint_stub_name` to `rotten-pdf-v1` (NOT a naive re-upsert, whose UPDATE path resets status to `'pending'` and would trip reverify's pending-skip — the test asserts status is still `'active'` after the re-point, BEFORE reverifying), reverifies (fails, gate-drops), then RESTORES the original stub and reverifies clean — both legs of the episode's acceptance criterion.

In `tests/reverify.test.ts`:

1. Happy path: fixture tool (pdf-extractor) reverifies → new `eval_runs` row with `triggered_by='reverify'`, score recomputed, still ≥ gate.
2. **Broken-tool acceptance (both legs, mechanism above)**: rot → score < 0.80 → absent from a subsequent discover (gate enforced in SQL), eval_runs row records the failures; restore → clean run, score recovers, tool discoverable again.
3. **Zero-rate trap lock**: a `tool`-kind row with an unknown `endpoint_stub_name` is `skipped: 'no-eval-suite'` — score UNCHANGED, no eval_runs row.
4. Catalog kind (skill) → `skipped: 'catalog-kind'`, untouched.
5. `--tool` filter reverifies exactly one tool.
6. `circuit_broken` tool: evals recorded, status still `circuit_broken` after.
7. Route: unfiltered sweep rejects non-admin; filtered accepts tool_author; response shape matches summary contract.
8. **Grader parity (R1 must-fix 1)**: malformed-bot's reliability_score is byte-identical before and after a sweep (the lenient override travelled with the shared helper).
9. Pending-status tool: `skipped: 'pending-status'`, untouched.
10. Push parity (cheap lock on the factored helper): `pdf-extractor-v3-1` publishes at its known 3/5 = 0.6 fixture outcome with `triggered_by='push'`.
